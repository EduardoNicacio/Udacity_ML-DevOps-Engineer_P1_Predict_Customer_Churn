# Instructions

## Objective

This project asks you to implement clean-code and software-engineering best practices. You do not need to build the data-science solution entirely from scratch.

The provided `churn_notebook.ipynb` identifies credit card customers who are most likely to churn, but it does not apply the engineering practices required for a production-ready codebase. Refactor the notebook to create, at minimum:

- `churn_library.py`
- `churn_script_logging_and_tests.py`
- `README.md`

## Choose a Repository Platform

Complete the project using the Udacity Workspace, GitHub, or Azure DevOps. Choose one workflow and use it consistently. The project files, implementation requirements, and rubric are the same for every workflow.

### Option A: Udacity Workspace

Start the Project Workspace and complete the files there. Download a backup of your work regularly.

If you use only the Workspace, you may use its **SUBMIT PROJECT** button. This option is not the Azure DevOps submission workflow because a Workspace-generated archive might not preserve the Git metadata from Azure Repos.

### Option B: GitHub

Open the public [project starter repository](https://github.com/udacity/cd0580-project-starter), then fork or clone it according to the repository instructions. If you clone a fork, replace `<your-github-username>` with your GitHub username:

```bash
git clone https://github.com/<your-github-username>/cd0580-project-starter.git
cd cd0580-project-starter
```

Commit and push your work regularly using meaningful commit messages.

### Option C: Azure DevOps

1. In Azure DevOps, create or open the private project in which you will store your work.

2. Import the following public starter repository into Azure Repos:

    ```bash
    https://github.com/udacity/cd0580-project-starter
    ```

3. Copy the clone URL displayed by Azure Repos and clone the imported repository:

    ```bash
    git clone https://dev.azure.com/<organization>/<project>/_git/<repository>
    cd <repository>
    ```

4. Confirm that `origin` points to the intended Azure Repos repository:

    ```bash
    git remote -v
    ```

5. Commit and push your work regularly using meaningful commit messages. Normal Git commands such as `git add`, `git commit`, `git pull`, and `git push` do not change when the remote is Azure Repos.

For detailed import and authentication instructions, refer to the current [GitHub to Azure DevOps Translation Guide](https://learn.udacity.com/ls15935?version=1.0&lessonKey=ls15935&conceptKey=7c109e93-bac0-48bc-8116-1aa73f7a5554). Udacity does not provide an Azure DevOps organization. Follow your organization's repository, security, and data-handling policies.

## High-Level Instructions

Refactor `churn_notebook.ipynb` into a modular Python codebase. Your completed project must include the following core files.

1. `churn_library.py`

    This module contains the functions used to identify customers who are likely to churn. You may complete the provided functions, change them, or add functions as needed to satisfy the rubric.

    The starter file includes function docstrings for one possible solution. See the Sequence diagram on the next page to understand the expected function calls.

    After defining the functions, you may add an `if __name__ == "__main__":` block so that the pipeline can be run from the command line:

    ```bash
    python churn_library.py
    ```

2. `churn_script_logging_and_tests.py`

    This file must:

    - contain tests for the functions in `churn_library.py`;
    - use assertions to confirm that returned values are not empty or that expected files and artifacts were created;
    - log understandable `INFO` messages for successful operations;
    - log understandable `ERROR` messages when exceptions occur; and
    - write the log output to a `.log` file in the `logs` directory.

    Testing and logging must work from the command line:

    ```bash
    python churn_script_logging_and_tests.py
    ```

    You may use a testing framework such as [pytest](https://docs.pytest.org/) as long as all rubric requirements are met.

3. `README.md`

The README must allow another person to understand and run the project without additional guidance. Include:

- project description;
- files and data description;
- installation or environment setup;
- how to run `churn_library.py`;
- how to run `churn_script_logging_and_tests.py`;
- the output locations for images, models, and logs; and
- the repository platform used for the project.

For an Azure DevOps submission, also include the Azure Repos URL and state that the private repository is supplied as a complete-repository ZIP containing the `.git` directory for offline review. The URL does not need to be accessible to the reviewer.

## Code Quality Considerations

### Style Guide (PEP 8)

Format the refactored code according to [PEP 8](https://peps.python.org/pep-0008/). These commands can assist with formatting:

```bash
autopep8 --in-place --aggressive --aggressive churn_library.py
autopep8 --in-place --aggressive --aggressive churn_script_logging_and_tests.py
```

### Linting (Pylint)

Run Pylint to identify programming errors and refactoring opportunities:

```bash
pylint churn_library.py
pylint churn_script_logging_and_tests.py
```

Both files must score at least `7.0`, with no critical errors. A score of `8.5` or higher is recommended.

### Docstrings

Every function must have a docstring that identifies its purpose, inputs, and outputs. Every Python file must have a module-level docstring that identifies the file's purpose, author, and creation date.

### Final Expectation

Your completed project directory must include, at minimum:

- `churn_library.py`
- `churn_script_logging_and_tests.py`
- `README.md`

It must also include the supporting artifacts generated by the pipeline:

- `data/bank_data.csv`
- `images/eda/`
- `images/results/`
- trained model files in `models/`
- the execution log in `logs/`

Review the project rubric before you begin and again before you submit. Follow the platform-specific instructions on the Project Submission page.
