# Rubric

Use this project rubric to understand and assess the project criteria.

## Code Quality

### Criteria

The code follows the PEP 8 coding style.

### Submission Requirements

All code written for this project follows the [PEP 8 guidelines](https://www.python.org/dev/peps/pep-0008/). Objects have meaningful names, code is appropriately commented and organized, and imports are correctly ordered.

Specifically:

- names use `snake_case` where appropriate;
- line length is no greater than 100 characters;
- imports are properly grouped; and
- there are no unused variables or imports.

The following commands can assist with formatting:

```bash
autopep8 --in-place --aggressive --aggressive churn_library.py
autopep8 --in-place --aggressive --aggressive churn_script_logging_and_tests.py
```

Both Python files meet the following Pylint requirements:

- minimum score: `7.0`;
- recommended target: `8.5` or higher; and
- no critical errors.

```bash
pylint churn_library.py
pylint churn_script_logging_and_tests.py
```

### Criteria

The README provides a project overview and instructions for using the code.

### Submission Requirements

The README clearly describes the project and allows a user to run it without additional guidance.

It includes:

- a project description;
- files and data descriptions;
- how to run the pipeline:

    ```bash
    python churn_library.py
    ```

- how to run the tests:

    ```bash
    python churn_script_logging_and_tests.py
    ```

- the output locations:

  - `images/eda/`
  - `images/results/`
  - `models/`
  - `logs/churn_library.log`

- the repository platform used for the project: Udacity Workspace, GitHub, or Azure DevOps.

For an Azure DevOps submission, the README also includes:

- the Azure Repos repository URL; and
- a statement that the private repository is supplied as a complete-repository ZIP containing the `.git` directory for offline review.

The Azure Repos URL does not need to be accessible to the reviewer.

### Criteria

All functions and Python files have docstrings.

### Submission Requirements

All functions and Python files include docstrings.

Function docstrings identify:

- purpose;
- input parameters; and
- output.

File-level docstrings identify:

- purpose;

- creation date.

## Testing & Logging

### Criteria

Tests are written for each function.

### Submission Requirements

- The provided test functions in `churn_script_logging_and_tests.py` are completed.
- Each test runs without errors.
- Tests include basic assertions that verify returned outputs are not empty and that expected files and artifacts are created.

### Criteria

Successful operations and errors are logged.

### Submission Requirements

- Logging is implemented with Python's `logging` module.
- `INFO` messages are recorded for successful execution.
- `ERROR` messages are recorded when exceptions occur.

### Criteria

Logs are stored in a `.log` file.

### Submission Requirements

- Logging output is written to a `.log` file.
- The `.log` file is created when the test script is executed.
- The file contains log messages after execution.

### Criteria

Error and information messages are easy to understand.

### Submission Requirements

Log messages indicate:

- which test or function is running; and
- whether it succeeded or failed.

Messages are understandable at a basic level and may use terms such as `SUCCESS` and `ERROR`.

### Criteria

Testing and logging can be completed from the command line.

### Submission Requirements

The README explains how to run the tests and generate the log file. Running the following command, or an equivalent documented command, executes the tests and produces the `.log` file:

```bash
python churn_script_logging_and_tests.py
```

## Problem Solving

### Criteria

The code completes the data-science process.

### Submission Requirements

The code in `churn_library.py` completes:

1. exploratory data analysis;
2. feature engineering, including categorical-variable encoding;
3. model training;
4. prediction; and
5. model evaluation.

### Criteria

Categorical columns are handled efficiently.

### Submission Requirements

The code uses one-hot encoding or the mean response to encode categorical columns. The inefficient repeated operations shown in the notebook are refactored, for example by looping over a list of categorical column names. The resulting implementation is easy to extend.
